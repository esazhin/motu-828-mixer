## 0 · Sections guide — how to read this document

This contract is the agreed scope of one delivery: what will be built, how it will be judged, and the
design the build follows. **§1–§5 state the agreement** — the problem, the solution direction and the
properties it guarantees, the working context, the plan with its acceptance criteria, and the runbook.
**§6–§7 are the derived build plan and binding design**; **§8 is appended when the delivery completes.**

A build that WALKS this contract reads five forms out of it, and reads nothing else about its
structure. They are prose within the frozen headings and table columns below; a contract missing one
is returned to review naming the row rather than half-planned.

1. Section role. Directly under a heading, one line `Role: binding — <why>` or
   `Role: informational — <why>`. Binding sections are carried to the builder IN FULL; informational
   ones are carried by pointer only. A contract stating no roles gets the default binding set
   (§2.5, §3.5, §4.2, §6.1, §7, §7.2) and a loud note that the default was used.
2. Task-row ownership. In §6.1's `design_refs` column: `OWNS: <paths>; TOUCHES: <paths>;
   BINDS: <seam>:<from|to>, …; DISCHARGES: <acceptance ids>; WIRES: <seam ids>` — semicolon-separated,
   any clause omitted when empty. This is where a seam SIDE is attached to the task that owns it;
   free-prose name matching across the §7.2 from/to columns is not a substitute. `WIRES` names the
   seams a task composes (both of their sides this design's): its piece proves each is wired.
3. Acceptance-row identity. In §4.2's first column: `<row id> · <sub-outcome id>` — the row's OWN
   stamped id first, then the sub-outcome it realizes. Several rows share a sub-outcome; only the
   row id can be discharged by exactly one task.
4. Artifact line. In §7's `layout`, one line per module: `` - `path` — responsibility — layer: <layer> ``
   where layer is one of contract / domain / application / infrastructure / wiring / presentation / edge / document.
   The layer is what orders the build inward-first.
5. Size bound. In §7, one line `Size bound: <n> artifacts per unit.` — a task row naming more splits
   mechanically, each split keeping its own seam sides and acceptance rows.

Reviewing: **§4.2 (Acceptance) and §7.2 (Seams) are the heart** — every §4.2 row is an observable
behaviour the delivery must demonstrate, and every §7.2 row is an internal connection a test must
actually execute. Place corrections at the specific row or clause they concern — the section structure
itself is fixed.

## 1 · Intent
Role: informational — the problem and its why; the builder is aware of it and never acts on it.
- **outcome:** The user wants to control the MOTU 828 audio interface's internal mixer and output routing (the main-mixer functionality of MOTU's CueMix 5: per-bus channel levels, pan, mute, solo, stereo linking, bus master level/mute, and which source feeds each output) from their Linux machine, without CueMix, from any browser on their home network (phone, tablet or PC). What the user sees must always match the unit, including changes made on the unit itself or after it is unplugged and replugged. It must be safe: it must never create a feedback loop between the 828's S/PDIF input and output (their Axe-Fx III sits on both ends), never change phantom power, preamp gain or pad, and refuse to write anything when the unit's model or protocol version is not the one the control protocol was verified against.

### 2.2 Summary
- **summary:**
  The user can run the 828's main mixer and output routing from any browser on their home network, with no CueMix.
  Every screen always shows what the unit actually holds, including changes made on the unit itself and after an unplug and replug.
  Anything that would loop the Axe-Fx's S/PDIF signal back into itself is refused with a clear message, and nothing is sent to the unit.
  Phantom power, preamp gain and pad cannot be changed from this app at all.
  If the unit reports a model or firmware protocol the app was not verified against, it only displays and warns, and writes nothing.

### 2.3 Ideality — what it optimizes for / deliberately trades
- **Optimizes for:**
  Every safety rule (the S/PDIF loop guard, the allowlist of property ids that excludes 48V, gain and pad, and the read-only mode when model or API version drifts) sits in the one service write path, so no browser and no bug in the web page can get around it.
  What every browser shows comes from one state model in the service, fed by the device stream and rebuilt from the full dump after any replug. Phone, tablet and PC therefore always agree with each other and with the unit.
  Fader moves feel instant in the browser because the service applies them optimistically and lets the device's own reports correct them.
  Each open protocol question (stereo-pair column semantics, live echo of writes, the mute, bus-master and routing write paths) is one setting in one module, so a result from W2–W5 changes one value, not the mixer code.
  Almost all acceptance scenarios run with no hardware against a fake 828 built from the real fixture, so the builder can work test-first without touching the unit.
- **Deliberately trades away:**
  The S/PDIF guard is conservative. It refuses any change that leaves a bus carrying S/PDIF in with an unmuted, non-zero fader routed to S/PDIF out, even at a level the user might consider harmless. To get such a route the user has to change the mix first.
  No live testing of real mix cells: the live tier touches only the unused PROTOCOL-SPEC §9 cells, so live behaviour on cells the user actually listens through is inferred from those cells.
  Stereo pairs are written to both columns until W4 proves the device needs only one. That doubles the MIDI messages for linked pairs.
  While the service holds the control port, CueMix under Wine and the tools/ scripts cannot use it until someone explicitly asks the service to release it.
  No login on the LAN page: anyone on the home network who opens port 5057 can move the mixer, within the safety guards.
  Out of scope for this delivery: EQ, gate, compressor, reverb, talkback, clock and preamp controls, even though the protocol exposes them.

### 2.6 Assumptions
Scales: **importance** = impact if the assumption is false (0 = none → 10 = the delivery is impossible as contracted) · **uncertainty** = what is actually known (0 = a known fact or proven → 10 = no clue, and the truth may be the complete opposite). A sum ≥ 17 is either **resolved** (settled before this contract shipped — the evidence is in `resolution`) or **escalated** (only the stakeholder can settle it: it is NOT a fact, it is listed under §1 to validate first, and its last column gives the easiest way to validate it and what changes if it is false). Rows `q…` are the answers this design assumes to points the stakeholder can decide; one the stakeholder answered is resolved by that answer. Rows `d…` sweep the terms of the ask: one row per class a term admits, its `kind` the lens it was found through (`quality` for a quality word's measure); a forced class is resolved by the reasoning in `resolution`, followed by what settles it outside this design (`source:` a definition, common knowledge, a repository path, the run environment, a prior, or the ask's own words quoted), a chosen one states the treatment this design picks and is graded like any other row.

## 5 · Execution notes
The build proceeds in this order: verify the §2.1 priors first (especially any linchpin), orient in the
§3 context and the repository's own docs, then realize each §4.1 leaf — tests first, implementation,
its §4.2 acceptance as the gate — checking change impact before edits and reusing what exists rather
than rebuilding it. Work outside the executor's reach is flagged, never silently skipped; the outcome
is self-reported to §8.

### 7.1 Design decisions
| decision | principle preserved |
|---|---|
| MixerService in `_motu_mixer/application/mixer_service.py` applies an accepted change to MixerState and publishes it before the device answers, and every later device Report overwrites that state. Optimistic display and truthful display become one model. | SRP / single source of truth (aggregate owned by one service) |
| SpdifLoopGuard in `_motu_mixer/domain/loop_guard.py` judges a hypothetical MixerState.with_writes copy before WriteScheduler.submit, so a refused change sends zero bytes. The write gate waits for complete GATE_ARRAYS so the guard never judges a half-received dump. | Clean architecture (pure domain rule, I/O-free) + fail-safe by construction |
| Writability comes from the single PROPERTY_TABLE in `_motu_mixer/domain/properties.py`, and actions.plan refuses any other id. 5004, 5001 and 5003 have no write path at all. | OCP / cascade collapse (one table drives codec type, index range and allowlist) |
| DeviceSession in `_motu_mixer/application/session.py` gives up the '828 COM' port on release() and takes it back on acquire(). Every reconnect starts a fresh MixerState through begin_session/end_session. | SRP (lifecycle separate from mixer logic) + DIP (ControlPort/PortLocator ports) |
| Simulated828Port in `_motu_mixer/infrastructure/simulated_828.py` substitutes for the real unit behind ControlPort and replays the real 2026-10-12 capture, so every §7 scenario except the live writes is proven with no hardware. | LSP + DIP (port substitution enables in-memory doubles) |
| Each remaining [TBD] (echo; W2/W3/W5) is one declared entry in `_motu_mixer/domain/protocol_bounds.py` with the single behaviour the design carries. No switches exist: optimistic apply plus overwrite is correct whether or not the device echoes. | Ubiquitous language + explicit bounded assumptions (no hidden modes) |
| Linked pairs write exactly one cell, via topology.primary_cell in `_motu_mixer/domain/topology.py`, as CueMix does (a2). Pan is visible only on stereo tabs and never on linked input strips (a3). | Domain model matches real-world invariants (CueMix [CODE]) |
| Transport is ALSA rawmidi through ctypes libasound in `_motu_mixer/infrastructure/alsa_rawmidi.py`. The port is resolved by an exact name match on `amidi -l`. python-rtmidi is not used (a1). | Infrastructure behind a port; adapter chosen by verified evidence |
| `_motu_mixer/protocol/sysex.py` holds every encode/decode pair (pack7/unpack7, encode_set/classify_host_frame, encode_report/decode), so the service and the simulator cannot drift. | Emit and parse together (inverse pairs co-located) |
| `_motu_mixer/presentation/view_model.py` is the only serializer for snapshot, delta, status and outcome, and the only parser of actions. The page renders from the served 'layout' section and holds no device catalogue. | SRP + no duplicated knowledge across language boundary |
| `_motu_mixer/application/write_scheduler.py` keeps the latest value per Address, sends at most 50 per second per Address, always sends the final value, and drops pending frames on detach. | SRP (rate and ordering isolated from mixer rules) |

### 7.3 Seam clauses
Role: binding — each seam's contract, clause by clause: an expectation is what the consumer sends, which the supplier must accept; an answer is what the consumer relies on getting back, and when. Every clause is proven on both sides — by the consumer's test over a double and by the supplier's test of the real thing. Where the supplier is a third party outside the design, our side is the test of how we USE it, and its side is the clause's `basis`: `documented: <where its documentation says so>`, `assumption <a §2.6 id>` (relied on, not guaranteed — validated as its grade says), or `customer-ci` (a supplier the customer's organisation owns, whose CI runs our consumer contract). Clauses whose supplier is in this design leave `basis` empty.
